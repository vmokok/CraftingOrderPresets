# Crafting Order Presets — design

Date: 2026-09-28. Status: approved in conversation, awaiting review of this
document.

## 1. Purpose

Placing many identical crafting orders through the standard customer order
form means filling in the same recipe, recipient, customer-provided reagents
with their quality, minimum quality, tip, duration and note every time. The
motivating case is a raid supplier placing about twenty cauldron orders twice
a week.

The addon records an order placed once through the standard form, stores it
under a name, and places it again with one click per order.

Non-goals:

- **Placing many orders with one click.** `C_CraftingOrders.PlaceNewOrder`
  carries `HasRestrictions`, the same flag as the auction house posting
  functions, and the Blizzard form only calls it from a button click. One
  click per order is the design, not a limitation to work around.
- Crafter-side features (claiming, fulfilling, scanning orders).
- Editing a preset field by field. A preset is changed by placing one order
  through the form and saving it again.
- Migrating Blizzard's order table across patches. When Blizzard renames a
  field (12.0.0 renamed `reagentItems` to `reagentInfos`), presets recorded
  before the patch are re-recorded. Future renames cannot be predicted.

## 2. Verified background

All references are to `Gethe/wow-ui-source`, branch `live`, commit `09b9db7`
(`12.1.0 (69933)`), the same build as the retail client used for testing.

- `C_CraftingOrders.PlaceNewOrder(orderInfo)` takes `NewCraftingOrderInfo`:
  `skillLineAbilityID`, `orderType`, `orderDuration`, `tipAmount`,
  `customerNotes`, `reagentInfos` (`RegularReagentInfo[]`: `reagent`,
  `quantity`), `craftingReagentItems` (`CraftingReagentInfo[]`: `reagent`,
  `dataSlotIndex`, `quantity`), optional `minCraftingQualityID`,
  `orderTarget`, `recraftItem`. `reagent` is `CraftingReagent`: optional
  `itemID`, optional `currencyID`.
  (`Blizzard_APIDocumentationGenerated/CraftingOrderUISharedDocumentation.lua`,
  `TradeSkillUITypesDocumentation.lua`.)
- The form builds that table in `ProfessionsCustomerOrderFormMixin:ListOrder`
  (`Blizzard_ProfessionsCustomerOrdersForm.lua`) and calls it from the
  `ListOrderButton` click handler or from the accept callback of its warning
  popup.
- The server answers with `CRAFTINGORDERS_ORDER_PLACEMENT_RESPONSE(result)`,
  `result` being `Enum.CraftingOrderResult`. Codes include `Ok`,
  `MissingItem`, `MissingNpc`, `MaxOrdersReached`
  (`ProfessionConstantsDocumentation.lua`). `MissingNpc` confirms the order is
  placed only while talking to the crafting orders NPC.
- An addon calling `PlaceNewOrder` from a button click with a copy of the
  form's table works: confirmed in game on 2026-09-28 by the owner with the
  prototype (Cauldron Orders, section 10).
- The form counts the customer's reagents with
  `ProfessionsUtil.GetReagentQuantityInPossession(reagent,
  transaction:ShouldUseCharacterInventoryOnly())`, which for items calls
  `ItemUtil.GetCraftingReagentCount(itemID, characterInventoryOnly)`:
  `C_Item.GetItemCount(itemID, true, false, true, not characterInventoryOnly)`,
  that is bags, bank, reagent bank and, unless the flag is set, the warband
  bank. Currencies use `C_CurrencyInfo.GetCurrencyInfo(id).quantity`. Nothing
  in `Blizzard_ProfessionsCustomerOrders` sets the inventory-only flag;
  callers outside that folder were not checked.
- The form disables its button when `depositCost + tip > GetMoney()`, with
  `depositCost = C_CraftingOrders.CalculateCraftingOrderPostingFee(
  skillLineAbilityID, orderType, orderDuration)`.

Existing addons, surveyed 2026-09-28 on CurseForge, Wago, WoWInterface and
GitHub (by repository name only; GitHub code search was not available):

- Profession Shopping List is the only real overlap. Its Quick Order builds the
  table by hand: tip fixed at 100 copper, empty note, no
  `minCraftingQualityID`, reagents picked automatically at the lowest quality
  owned, basic reagents only, one recipient per recipe, repeat of the last
  order only, data per character (`modules-old/CraftingOrders.lua`, commit
  `5c506b8`).
- No addon found stores several named presets captured from the form.

## 4. Code structure

Three files, loaded in this order. They share the addon namespace
(`local _, ns = ...`). Nothing else reaches `_G` except the saved variable,
the slash command globals and its `SlashCmdList` entry.

| File | Responsibility |
|---|---|
| `Locale.lua` | Table `ns.L`. The key is the English string itself; a missing translation falls back to the key. Translations: enUS (keys), ruRU. |
| `Core.lua` | Saved data, capture of form orders, placement and its state, capacity calculation, slash commands. Knows nothing about frames; announces changes through a callback. |
| `UI.lua` | Panel, dropdown, tooltip, collapse, anchoring to the orders window. Reads and changes data only through `Core` functions. |

## 5. Data model

Saved variable `CraftingOrderPresetsDB`, account-wide:

```lua
{
    schemaVersion = 1,
    presets = {
        [name] = {
            order = { ... },   -- the exact table the form passed to PlaceNewOrder
            recipe = "...",    -- recipe name at capture time, may be nil
            build = "...",     -- client build at capture time (GetBuildInfo)
            savedAt = 0,       -- time() when saved
        },
    },
    last = { order = ..., recipe = ..., build = ..., savedAt = ... },
    selected = "...",          -- name of the selected preset, may be nil
    collapsed = false,
}
```

`schemaVersion` is for migrating the addon's own data in later versions.
`build` is shown in the tooltip so a user can tell a preset recorded before a
patch.

## 6. Behaviour

### 6.1 Capture

`hooksecurefunc(C_CraftingOrders, "PlaceNewOrder", ...)` runs after every
call. If the argument is the table the addon itself just sent, it is ignored.
Otherwise a deep copy becomes `last`, with the recipe name read from
`ProfessionsCustomerOrdersFrame.Form.order.spellID` through
`C_Spell.GetSpellName`. The copy is taken when the order is sent, before the
server answers, so a manual order the server rejects is still offered for
saving; the user sees the rejection in the form.

### 6.2 Placement

States: idle and pending.

- Idle, click on Place: send a deep copy of the preset. If an
  `ADDON_ACTION_BLOCKED` or `ADDON_ACTION_FORBIDDEN` naming this addon
  arrived during the call, report it and stay idle. Otherwise become pending.
- Pending: the Place button is disabled; a slash command place reports that
  the previous order is still waiting.
- `CRAFTINGORDERS_ORDER_PLACEMENT_RESPONSE` while pending: back to idle. `Ok`
  increments the per-preset session counter. Any other code is reported the
  way the form reports it: `InvalidTarget`, `TargetCannotCraft` and
  `MaxOrdersReached` with the client's own localized strings
  (`CRAFTING_ORDER_FAILED_INVALID_TARGET`, `CRAFTING_ORDER_FAILED_TARGET_CANT_CRAFT`,
  `PROFESSIONS_MAX_ORDERS_REACHED`), everything else with
  `PROFESSIONS_ORDER_PLACEMENT_FAILED` followed by the
  `Enum.CraftingOrderResult` name, so a report names the exact code.
- No response within 15 seconds: back to idle, reported. The number has a
  margin and was not measured. A timer from an earlier order never ends a later
  pending order.
- A response while idle belongs to an order placed through the form and is
  ignored.

Known ambiguity: an order placed through the form while one of ours is
pending makes the first response count as ours. Accepted; the form shows its
own result.

### 6.3 Capacity ("enough for N")

For the selected preset:

- reagents: sum the required quantity per `itemID` (and per `currencyID`)
  over `reagentInfos` and `craftingReagentItems`, skipping zero quantities;
  owned amount by the same functions the form uses (section 2); count
  `floor(owned / required)`;
- money: `floor(GetMoney() / (CalculateCraftingOrderPostingFee(
  skillLineAbilityID, orderType, orderDuration) + tipAmount))` when the
  divisor is positive;
- N is the minimum; the line names what runs out first.

Recalculated on selection change, `BAG_UPDATE_DELAYED`, `PLAYER_MONEY`, and
after every placement response. N = 0 colours the line red but does not
disable Place: the server decides, the count is a hint, and a wrong hint must
not block a valid order.

### 6.4 Panel

Anchored to the right of `ProfessionsCustomerOrdersFrame`; while the form's
`CurrentListings` popout (anchored to the right of the form) is visible, to
the right of the popout instead.

Expanded, top to bottom: title with collapse button; preset dropdown and
Delete; two-line summary (recipe; recipient, tip, reagent stacks); Place;
status line; capacity line; "Last order placed through the form" with its
summary; name box prefilled with the recipe name, and Save.

Collapsed: title, selected preset name, Place. The state persists in
`collapsed`.

The dropdown (`WowStyle1DropdownTemplate`) rebuilds its menu only when the set
of names changes. Selecting an entry runs inside the click on the open menu,
and `GenerateMenu` on an open menu reinitialises it without closing
(`DropdownButtonMixin:RegisterMenu`); selection only updates the text.

### 6.5 Tooltip

On hover over the dropdown and over the summary: recipe and capture build;
recipient type and name; tip; posting fee; duration; minimum quality; each
customer reagent as quality icon, name, quantity. Items not yet cached show
`item:<id>` and refresh when the client loads them. The API for the quality
tier icon and for turning `minCraftingQualityID` into a tier is to be read
from the 12.1 source during implementation (section 9).

### 6.6 Slash commands

`/cop` and `/craftingorderpresets`:

- `place [name]` places the named preset, or the selected one;
- `show [name]` prints a preset's table, or `last`;
- `list` lists names;
- anything else prints help.

`place` from a macro is a hardware event like a button click.

## 7. Localization

`ns.L[key]` with the English string as key. ruRU is shipped. Recipe and item
names come from the client in its own language. All user-visible text,
including chat output and error reports, goes through `L`.

## 8. Testing

The test harness is a small Go program in `tests/` (own `go.mod`) that runs
the addon under gopher-lua, which implements Lua 5.1 like the game client,
against stubs of the WoW API. Stubs follow the behaviour read in the Blizzard
source (section 2); fixture orders carry every field of `NewCraftingOrderInfo`.

- Every behaviour change starts with a failing test.
- Key behaviours get a deliberate mutation of the code to confirm a test
  catches it.
- The harness checks that loading the addon adds no globals beyond the
  allowed ones.
- The harness checks the locale: every `L["..."]` key in the code has a ruRU
  entry, no ruRU entry is unused, and format specifiers match.
- CI also runs luacheck. It is not installed locally; the global check above
  covers leaks locally.

## 9. Not established

- Whether the server takes customer reagents from the warband bank and the
  character bank, as the form's count suggests. Checked in game before
  release (section 11); if not, capacity counts only what the server takes.
- The value of the `MaxOrdersReached` cap.
- Whether the server throttles orders beyond waiting for each response.
- The API for the quality tier icon and the `minCraftingQualityID` to tier
  mapping (to be read from source).
- Whether `/cop` collides with another popular addon's slash command.
- Whether CurseForge offers an API to create a project; assumed manual.

## 10. Prototype data

The prototype, Cauldron Orders, lived only in the AddOns folder with saved
variable `CauldronOrdersDB` (`orders`, `last`, `selected`). Its two presets
are converted locally into `CraftingOrderPresets.lua` in the shape of section 5,
with the game closed because the client rewrites saved variables on logout.
The conversion is not part of the shipped addon: nobody else has that data.

## 11. In-game acceptance before v1.0.0

1. Panel present; the two converted presets listed and placeable.
2. Tooltip matches what the form shows for the same recipe.
3. Capacity matches the form. Separately: reagents only in the warband bank —
   does the server accept the order?
4. Collapsed state survives `/reload`.
5. ruRU interface in the owner's client; enUS fallback covered by tests.
